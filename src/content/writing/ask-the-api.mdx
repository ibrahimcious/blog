Field notes from [Siverina](/siverina), before the write-up gets tidier than the day was.

- **Feature.** A chat widget that answers from the app's existing user guide and falls back to a WhatsApp contact when it can't help.
- **Grounding.** The whole guide, sent with every request. No retrieval index, no stored conversation history.
- **Provider.** Sumopod, an OpenAI-API-compatible reseller, model `deepseek-v4-flash`.
- **Status.** Verified end to end from this machine. The live site is still returning its fallback message — the cause isn't confirmed yet.

The app already had a user guide. Nine dense pages covering three different roles, generated as a PDF from a script that hardcoded every paragraph as JSX, plus a shorter version of the same material on an in-app page for people who haven't registered yet. The request was to put a chatbot in front of both of them: answer the ordinary questions people actually ask — how do I register, what documents do I need — from that existing text, and when it can't help, hand the person to the WhatsApp number the tax office already staffs for exactly that.

## What I didn't build

The obvious shape for this is retrieval: chunk the guide, embed it, store the embeddings somewhere, search them per question. I didn't build that. Nine pages of text fits inside a modern model's context window without any strain, so the plan became handing the whole guide to the model on every request instead of building a search index for a document short enough to just read in full. The day before, the same logic had already shown up once, on a different feature: checking a taxpayer's registration number against a government tax database live, on every signup, instead of syncing a copy of that database into this app's own storage. Neither problem was actually short of data. Both were short of a reason to keep a copy of someone else's data at all.

## One copy of the truth

The guide's actual words lived in exactly one place: a script that built a PDF by hardcoding every heading, paragraph, and table as JSX. If the chatbot was going to answer from "the guide," it needed to read the same words that script rendered, not a second copy that would drift the moment someone edited one and forgot the other. I pulled the content out into a plain data file, tables and colored callout boxes and all, and rewrote the PDF script to render from that data generically instead of by hand.

Regenerating the PDF afterward produced a file 67 bytes different from the one it replaced, with the same twelve pages. I paged through the output and checked a table cell with a hint line under it, a colored callout box, and a bolded phrase inside a bullet point against what they looked like before the rewrite. All three matched.

## Which provider, exactly

The one detail I couldn't reuse from anything already in the app was which service would actually answer the questions. I asked.

- **Round one.** "Which LLM API should the chatbot call?" — "Something else."
- **Round two.** Three named providers offered as a shortcut — "Something else," again.
- **Round three.** "What's the exact name of the provider you want?" — an Indonesian API reseller called Sumopod, running a DeepSeek model, described as "DeepSeek Flash."

## The model that wasn't quite real

Sumopod turned out to speak the same wire format as OpenAI's API, which meant the official OpenAI client library would talk to it just by pointing its base URL somewhere else. That part was easy. "DeepSeek Flash" was not, quite — it's the kind of name a person remembers rather than the exact string a catalog uses, and hardcoding a guess into the one field that has to match exactly is how a feature ships broken on every single request. Sumopod's API answers a plain models listing, so once a real key existed I asked it instead of asking a person to go check a dashboard.

```
curl -H "Authorization: Bearer sk-••••••••" \
  https://ai.sumopod.com/v1/models

{"id":"deepseek-v4-flash","mode":"chat","max_input_tokens":1000000}
```

`deepseek-v4-flash`. Close enough to what I'd been told to prove it was the right family of model, different enough that typing the remembered name instead would have quietly pointed the whole feature at a model that plain does not exist.

## Borrowed rules, not new ones

Everything else about how this integration behaves was already decided by two other integrations already living in this app: never let an external call throw, always return a value that says plainly whether it worked, go quiet instead of erroring when a credential is missing, put a timeout on every request, never retry on a path a person is sitting in front of waiting. I didn't reinvent any of that for a chatbot. I copied the shape of the code already handling outbound WhatsApp messages and the tax-registry lookup, because a third external service breaking a workflow people already depend on gets meaner to debug, not more distinctive.

## What it actually said

With a real key in place, I asked it three questions before anyone else did.

> Bagaimana cara daftar sebagai Wajib Pajak?
>
> Buka halaman utama, klik "Daftar sebagai Wajib Pajak", isi NPWPD, nama perusahaan, nomor HP, dan password minimal 8 karakter...

> Kapan batas pengajuan bulanan?
>
> Batas pengajuan bulanan saat ini adalah tanggal 10...

> Siapa presiden Indonesia?
>
> Maaf, saya tidak bisa membantu pertanyaan di luar cakupan panduan aplikasi... silakan hubungi Pelayanan melalui WhatsApp.

The first answer was the actual registration steps, correctly, in plain prose. The second answered with the real configured deadline rather than a stale example, which meant the one fact in the guide that changes without a redeploy was actually being read fresh on every request instead of baked in once. The third, asked deliberately, declined, said as much, and pointed at the WhatsApp number, instead of answering a question the guide has nothing to say about.

## Shipping dark, then an open question

The feature deployed with both the provider key and the model name left empty everywhere except my own machine, which means it went live already inert — the same code path, always answering "not configured," always showing the fallback contact instead of an answer. That's the safe way to ship something that costs money per request into a system you don't want to accidentally switch on for the whole internet at once.

Then a screenshot came in from the real site. Someone had typed a question into the widget and gotten the same fallback message the code shows for two entirely different reasons. Maybe the key still isn't set on the server. Maybe it is, and the server can't actually reach Sumopod, the same way it once couldn't reach the tax registry until a routing problem got sorted out. The message on screen looks identical either way.

Which one it actually is isn't something a screenshot can answer. Only the machine can, which is exactly what I've asked to go check.
